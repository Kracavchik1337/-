# Техническая документация информационной системы автоматизации пекарни-кондитерской «Tasty Buns»

Данная документация представляет собой полное описание архитектуры данных (ER-модели), проектирования пользовательских интерфейсов (UI/UX) и сквозной бизнес-логики ИС для автоматизации кондитерского производства и розничных продаж.

---

## 1. Архитектура и детальное описание базы данных (ER-диаграмма)

База данных спроектирована по правилам третьей нормальной формы (3NF) для исключения избыточности данных и аномалий модификации. Структура разделена на 4 функциональных контура.

### Контур А: Персонал и пользователи
#### 1. Таблица `Employee` (Персонал пекарни)
*   **Бизнес-логика:** Хранит мастер-данные сотрудников, определяет их права доступа через роли (`position`) и контролирует их статус (уволен/активен) для блокировки авторизации.
*   **Атрибуты:**
    *   `employee_id` (INT, PK, AUTO_INCREMENT) — уникальный код сотрудника.
    *   `full_name` (VARCHAR(150), NOT NULL) — ФИО сотрудника.
    *   `position` (VARCHAR(50), NOT NULL) — должность (Пекарь, Кассир, Кладовщик, Администратор).
    *   `phone` (VARCHAR(20), NOT NULL, UNIQUE) — мобильный телефон (служит логином в систему).
    *   `hire_date` (DATE, NOT NULL) — дата официального трудоустройства.
    *   `status` (VARCHAR(20), NOT NULL) — статус контракта (`Active`, `Suspended`, `Terminated`).

### Контур Б: Складской учет сырья и снабжение
#### 2. Таблица `RawMaterial` (Склад ингредиентов и материалов)
*   **Бизнес-логика:** Управляет остатками сырья (мука, молоко, дрожжи, упаковка). Поле `min_threshold` используется для предиктивного анализа и автоматического формирования заявок поставщикам при дефиците.
*   **Атрибуты:**
    *   `material_id` (INT, PK, AUTO_INCREMENT) — код сырья.
    *   `name` (VARCHAR(100), NOT NULL, UNIQUE) — коммерческое наименование.
    *   `unit` (VARCHAR(10), NOT NULL) — базовая единица измерения (кг, л, шт).
    *   `current_stock` (DECIMAL(10,3), NOT NULL, CHECK >= 0) — текущий весовой/штучный остаток.
    *   `unit_price` (DECIMAL(10,2), NOT NULL, CHECK >= 0) — текущая средневзвешенная себестоимость единицы.
    *   `min_threshold` (DECIMAL(10,3), NOT NULL) — неснижаемый остаток.

#### 3. Таблица `Supply` (Документы поступления / Поставки)
*   **Бизнес-логика:** Регистрирует факт оптовой закупки сырья. Напрямую связана с `Employee`, фиксируя материально ответственное лицо, принявшее накладную.
*   **Атрибуты:**
    *   `supply_id` (INT, PK) — номер накладной.
    *   `employee_id` (INT, FK -> Employee) — сотрудник, оформивший приемку.
    *   `supplier_name` (VARCHAR(100), NOT NULL) — юридическое лицо поставщика.
    *   `supply_date` (DATETIME, NOT NULL) — фактическая дата и время разгрузки.
    *   `total_cost` (DECIMAL(10,2), NOT NULL) — общая сумма поставки (сумма всех позиций).
    *   `status` (VARCHAR(20), NOT NULL) — статус проводки (`Draft`, `Completed`, `Cancelled`).

#### 4. Таблица `SupplyItem` (Спецификация поставки)
*   **Бизнес-логика:** Реализует связь «многие-ко-многим» между накладными и материалами. Хранит историческую закупочную цену конкретной партии.
*   **Атрибуты:**
    *   `supply_item_id` (INT, PK) — ID строки спецификации.
    *   `supply_id` (INT, FK -> Supply) — ссылка на документ поставки.
    *   `material_id` (INT, FK -> RawMaterial) — ссылка на сырье.
    *   `quantity` (DECIMAL(10,3), NOT NULL) — объем поставки.
    *   `purchase_price` (DECIMAL(10,2), NOT NULL) — цена закупки за единицу товара.

### Контур В: Рецептура и производственный цех
#### 5. Таблица `Product` (Каталог готовой продукции)
*   **Бизнес-логика:** Мастер-каталог выпекаемых изделий для отображения на витрине и в мобильном приложении. Поле `shelf_life_hours` отвечает за контроль просрочки.
*   **Атрибуты:**
    *   `product_id` (INT, PK) — артикул изделия.
    *   `name` (VARCHAR(100), NOT NULL, UNIQUE) — наименование для витрины.
    *   `category` (VARCHAR(50), NOT NULL) — товарная группа (`Хлеб`, `Булочки`, `Сладкое`, `Пироги`).
    *   `price` (DECIMAL(10,2), NOT NULL) — розничная стоимость продажи.
    *   `shelf_life_hours` (INT, NOT NULL) — срок годности с момента выпечки.
    *   `status` (VARCHAR(20), NOT NULL) — доступность для заказа (`Active`, `Archived`).
    *   `stock_quantity` (INT, NOT NULL, DEFAULT 0) — доступное количество на витрине.

#### 6. Таблица `Recipe` (Технологические карты)
*   **Бизнес-логика:** Паспорт приготовления блюда. Поле `output_quantity` задает плановый выход единиц продукции при одном цикле замеса/выпечки по ТТК (технико-технологической карте).
*   **Атрибуты:**
    *   `recipe_id` (INT, PK) — ID техкарты.
    *   `product_id` (INT, FK -> Product) — целевой продукт.
    *   `instructions` (TEXT) — пошаговый алгоритм (замес, расстойка, температурный режим печи).
    *   `output_quantity` (INT, NOT NULL) — нормативный выход штук из одного замеса.

#### 7. Таблица `RecipeItem` (Ингредиенты техкарты)
*   **Бизнес-логика:** Норма расхода сырья на одну раскладку рецепта. Брутто-состав изделия.
*   **Атрибуты:**
    *   `recipe_item_id` (INT, PK) — ID строки состава.
    *   `recipe_id` (INT, FK -> Recipe) — ссылка на рецепт.
    *   `material_id` (INT, FK -> RawMaterial) — требуемый ингредиент.
    *   `quantity` (DECIMAL(10,3), NOT NULL) — норма расхода (например, 0.350 кг муки).

#### 8. Таблица `Batch` (Производственные партии / Выпечка)
*   **Бизнес-логика:** Учет работы производственного цеха. При закрытии партии статус `status = 'Completed'` триггерно увеличивает поле `Product.stock_quantity` на витрине пекарни.
*   **Атрибуты:**
    *   `batch_id` (INT, PK) — номер варки/партии.
    *   `recipe_id` (INT, FK -> Recipe) — по какому рецепту велось производство.
    *   `employee_id` (INT, FK -> Employee) — ответственный пекарь смены.
    *   `produced_at` (DATETIME, NOT NULL) — дата и время извлечения из печи.
    *   `quantity_produced` (INT, NOT NULL) — фактическое количество получившихся изделий.
    *   `status` (VARCHAR(20), NOT NULL) — статус партии (`In Progress`, `Completed`, `Rejected`).

#### 9. Таблица `BatchMaterial` (Фактический расход на партию)
*   **Бизнес-логика:** Фиксирует реальное количество списанных ингредиентов со склада во время замеса (с учетом возможных отклонений от идеальной рецептуры).

### Контур Г: Коммерция (Продажи и Убытки)
#### 10. Таблица `Sale` (Кассовые чеки)
*   **Бизнес-логика:** Фискальный заголовок транзакции розничной продажи в торговой точке или через приложение.
*   **Атрибуты:**
    *   `sale_id` (INT, PK) — номер чека.
    *   `employee_id` (INT, FK -> Employee) — кассир (или системный ID для онлайн-заказов).
    *   `sold_at` (DATETIME, NOT NULL) — дата-время фискализации.
    *   `total_amount` (DECIMAL(10,2), NOT NULL) — итоговая сумма к оплате.
    *   `payment_method` (VARCHAR(30), NOT NULL) — метод оплаты (`Cash`, `Card`, `SBP`, `Bonus`).
    *   `status` (VARCHAR(20), NOT NULL) — состояние чека (`Paid`, `Refunded`).

#### 11. Таблица `SaleItem` (Спецификация чека)
*   **Бизнес-логика:** Каждая строка проданного товара. Уменьшает физический остаток `Product.stock_quantity` на витрине.
*   **Атрибуты:**
    *   `sale_item_id` (INT, PK) — ID позиции в чеке.
    *   `sale_id` (INT, FK -> Sale) — ссылка на чек.
    *   `product_id` (INT, FK -> Product) — проданный товар.
    *   `quantity` (INT, NOT NULL) — количество штук в чеке.
    *   `unit_price` (DECIMAL(10,2), NOT NULL) — цена продажи с учетом скидок на момент закрытия чека.

#### 12. Таблица `WriteOff` (Акты списания)
*   **Бизнес-логика:** Журнал внутренних потерь предприятия. Позволяет утилизировать сырье (порча, истекший срок хранения муки) или готовую продукцию (непроданный вечерний хлеб, черствая выпечка).
*   **Атрибуты:**
    *   `write_off_id` (INT, PK) — номер акта списания.
    *   `employee_id` (INT, FK -> Employee) — инициатор списания (шеф-пекарь или управляющий).
    *   `material_id` (INT, FK -> RawMaterial, NULLABLE) — заполняется, если списывают ингредиент со склада.
    *   `product_id` (INT, FK -> Product, NULLABLE) — заполняется, если списывают готовую булку с витрины.
    *   `reason` (VARCHAR(255), NOT NULL) — причина списания (`Expired`, `Defect`, `Sanitary Waste`).
    *   `write_off_date` (DATETIME, NOT NULL) — дата проведения документа.
    *   `quantity` (DECIMAL(10,3), NOT NULL) — количество утилизированного объема.

## 2. Анализ и декомпозиция интерфейсов (UI/UX) и Пользовательские сценарии

Интерфейс мобильного приложения ориентирован на быстрый заказ (B2C-сегмент). Дизайн выполнен в нео-нуарном стиле с высокой контрастностью элементов для удобства чтения при слабом освещении (например, ранним утром при покупке кофе и хлеба).

### Пользовательский сценарий 1: Авторизация по номеру телефона
1.  **Действие:** Пользователь открывает приложение. Система проверяет наличие сессии. Если сессия отсутствует, отображается **Экран 1: Вход**.
2.  **Элемент контроля ввода:** Инпут номера телефона содержит жесткую маску `+7 (___) ___-__-__`. Символы отличные от цифр блокируются на уровне фронтенда.
3.  **Валидация:** При заполнении поля ввода и клике по интерактивной зоне, триггерится API-запрос проверки существования аккаунта. При отсутствии совпадений активируется анимация перехода на текстовую кнопку `Зарегистрироваться`.

### Пользовательский сценарий 2: Навигация по каталогу и выбор свежего хлеба
1.  **Действие:** После успешного входа открывается **Экран 2: Каталог**.
2.  **Визуальный фокус:** Верхний промо-баннер демонстрирует процесс выпечки (эмоциональный триггер свежести).
3.  **Фильтрация:** Нажатие на таб-переключатель категорий (например, `Хлеб`) плавно меняет состояние UI (активный таб инвертирует цвета, получая контрастную серую подложку). При этом отправляется асинхронный AJAX-запрос к БД для фильтрации плиточного интерфейса (Grid) без перезагрузки всего экрана.
